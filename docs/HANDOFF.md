## 2. 실측으로 배운 함정 (시간을 아껴줄 목록)

1. **3D가 검게 비면 코드부터 의심하지 마라.** 우선순위: ① 온보딩/모달이 화면을 대체 중인지 스크린샷 ② `canvas.getBoundingClientRect()`가 300×150이면 백그라운드 창 ResizeObserver 스로틀 (7b72b4a에서 마운트 시 resize 디스패치로 픽스됨 — 그래도 재발하면 `window.dispatchEvent(new Event("resize"))`) ③ 그래도 안 되면 React 이중 로드(.vite 삭제+재시작+새 탭). 이 순서를 안 지켜서 한 시간을 날린 적 있다.
2. **프리뷰 콘솔 도구는 모든 로그를 2배로 찍는다.** `console.log` 1회 테스트로 배율을 보정한 뒤 "배너 2번" 같은 시그니처를 판정해라.
3. **vite.config.ts를 저장하면 dev 서버가 자동 재시작 + dep 재최적화된다.** 직후의 브라우저 검증은 페이지 리로드 후에.
4. **PowerShell 5.1에서 따옴표 든 커밋 메시지는 here-string도 깨진다.** 커밋은 `git commit -F <파일>`로.
5. **electron 빌드 EBUSY** = `dist-installer/win-unpacked`의 앱이 실행 중. `Get-Process "Vision Engine" | Stop-Process` 후 재빌드.
6. **5199 포트를 물고 있는 정체불명 node** = 대개 데스크톱 셸이 스폰한 dev 서버다.
7. **QA/테스트가 workspace 실데이터를 오염시킨다** (feed.json, 채팅, GDD). 테스트 후 `git checkout -- workspace/...` 또는 생성물 삭제. 채용 테스트는 반드시 퇴사로 원복.
8. **NVIDIA 키는 이미지 함수권한이 없다**("Function not found for account") — env `VE_NVIDIA_IMAGE_URL`로 우회 가능. GitHub Models 무료 티어는 4,000토큰 제한.
9. 에이전트 산출물의 도구 호출 JSON 누수는 `sanitizeAgentOutput`이 이중 방어 중 — 로컬 모델 교체 시 재확인해라.
10. ~~PM kimi-k2.6 channels 오류~~ **해결(2026-07-11): PM을 nvidia/qwen/qwen3.5-122b-a10b로 교체** (백업: openclaw.json.bak-v39). 모델 비교 실측(같은 날): **직원은 next-80b 유지가 답** — 122b는 생성 3배 빠르지만(9s vs 29s) 콜드 스타트가 17~50초로 널뛰어(무료 티어 큐) 29명이 수십 콜 하는 회의에선 편차가 더 아프다. next-80b는 0.4~4초로 안정. PM은 호출이 적어 122b(신세대 품질) 유지. **397b는 게이트웨이 경유 시 첫 토큰 120초+로 idle 워치독에 잘림** — 에이전트용 금지. 신규 모델 5종은 프로필 🧠에서 선택 가능.
11. **openclaw.json/custom-agents.json을 PowerShell로 쓰지 마라** — PS 5.1 `ConvertTo-Json`이 최상위 배열을 `{value,Count}` 래퍼로 감싼다(v3.7에서 custom-agents.json 깨짐, node로 복구). 설정 JSON 쓰기는 node(`JSON.stringify`)로. 게이트웨이는 BOM 없는 UTF8만 파싱하므로 `[System.IO.File]::WriteAllText(...,UTF8Encoding($false))` 또는 node.
12. **`webapp/server/*.mjs`를 고치면 dev 서버를 재시작해야 반영된다** — 플러그인이 동적 import로 모듈을 캐시한다. vite.config.ts 저장은 자동 재시작을 트리거하지만 .mjs 단독 수정은 아니다.
13. **오너의 노션(app.notion.com)은 신형 API라 heading_4~6 블록이 실재한다** — 구식 가정(h1~3만)이면 헤딩 텍스트가 통째로 유실된다(슬라임 김치 기획서에 h4가 57줄). 가져오기(flatten)는 `####`로 살리고, 편집실은 마커로 보존한다.
14. **에이전트 페르소나(AGENTS.md)는 게이트웨이 시작 시점에 로드된다** — 파일만 고치면 반영 안 됨, 게이트웨이 재시작 필요. 그리고 `schtasks /End "OpenClaw Gateway"`가 실제 node 프로세스를 못 죽이는 경우가 있다(이틀 묵은 PID가 포트를 계속 물고 있었음) — 재시작이 안 먹으면 18789 포트의 PID를 직접 Stop-Process 후 `/Run`. 진행 중인 회의가 있으면 재시작하지 마라(호출이 끊긴다).
15. **아키비스트 산출물 길이 제한("20줄 이내")이 편집실 전문 반환과 충돌했었다** — 페르소나에 예외를 명시해 해결. 새 업무를 페르소나에 추가할 때 기존 산출물 규칙과 모순되지 않는지 확인해라. 또 qwen은 "## 헤딩으로 시작" 지시를 자주 무시한다 — store의 추가 모드 헤딩 자동 보정(요구의 따옴표 섹션명)이 이중 방어다.
16. **reflowMd는 서버(notion-publish.mjs)와 클라(lib/gdd.ts)에 같은 알고리즘이 2벌 있다** — 한쪽만 고치면 발행본과 앱 표시가 어긋난다. 수정 시 반드시 함께. 기존 GDD는 2026-07-11에 일괄 리플로우 마이그레이션됨(각 프로젝트에 GDD.md.bak-reflow 백업).
17. **게이트웨이 오류 문자열("LLM request timed out", channels, 메모리 인덱스 손상)이 에이전트 산출물로 저장돼 GDD를 오염시킨 실사례 있음**(2026-07-11 시장 확장 회의 — 동시 4에서 next-80b도 idle timeout 발생). `isGatewayErrorText`(lib/gdd.ts)로 3중 방어: 교차검토 수정본 폐기 / QA 재작성 폐기 / reflectToGdd 차단. 새 산출물 저장 경로를 만들면 이 가드를 함께 달아라.
18. **channels 오류는 kimi 전용이 아니다** — QA 디렉터(next-80b)에서도 간헐 발생(같은 날 16:56). 게이트웨이 레벨 이슈로 재현 조건 불명. 각 단계 폴백이 있으니 흐름은 완주하지만, 잦아지면 게이트웨이 재설치 검토.
19. **회의 산출물은 대표 통합까지도 오염될 수 있다** — 대표 통합본이 "모바일 F2P 동시 출시"처럼 원본 기획과 어긋난 사례(원본=PC Steam). 계층 폴백은 흐름을 보장할 뿐 내용 정합성은 보장하지 않는다 — 중요 회의는 오너(또는 대리)가 GDD를 대조 검증할 것. 회의록의 "검토·QA 근거"가 대조 시작점.

54. **"자리가 모자라 겹친다"는 방 크기가 아니라 `i % N` 때문이다 (2026-07-19 오너 발견)**: 오너가 "회의실이 너무 좁아서 겹쳐 들어가는 친구들이 있다"고 했는데, 실제 원인은 `MEET_SEATS`가 **8석 고정**이고 `meetingSeat(i) = MEET_SEATS[i % 8]`이었던 것 — 9번째 참석자부터 1번 자리에 **좌표까지 정확히 같게** 겹쳤다. 계층 오케스트레이션은 PM+팀장+담당+기여자로 **19~20명**이 모이므로 11명이 포개져 있었다. **처방**: 좌석을 인원수 `n`에서 계산한다(착석 14석 + 넘치면 뒤쪽 입석 2줄, 줄 안에서 균등 분배 → 간격만 좁아지고 절대 안 겹침). 방도 서편으로 넓혔다(폭 9.4→14.2, MEETING_CENTER x 3.5→1.0 — 대표실 x≤-8.5와 휴게실 x≥8.9 사이가 비어 있었다). 방을 키우면 **함께 따라가야 하는 것들이 있다**: 유리벽·테이블·스크린·카메라 프리셋·펜던트 조명(1등→3등, 안 늘리면 양 끝이 어둡다)·`atMeeting` 판정 반경(반경 3.6 원 → 사각 판정, 안 고치면 서편 끝 사람이 정면을 안 본다). **검증은 화면이 아니라 좌표로** 하라 — n=1..30에 대해 "모든 쌍의 거리 > 0" + "전원 벽 안"을 스크립트로 돌렸다(최소 간격 1.44, 캐릭터 반경 0.35).

55. **`useRef(0)` 기준값은 마운트를 "변화"로 오인한다 (2026-07-19 오너 발견)**: "회의 시작 시 회의실로 시선 이동"을 `prevMeetingCount = useRef(0)` + `if (n > 0 && prev === 0)`으로 구현했더니, **탭을 열 때마다 카메라가 회의실로 튀었다**(오너: "새 탭을 여는 형식이라 열 때마다 회의실로 가는 게 안 좋아 보여"). 마운트 시 ref가 0으로 새로 생기니 **진행 중인 회의가 매번 0→N 전환으로 읽힌 것**. **처방**: 기준값을 `useRef<number | null>(null)`로 두고 첫 실행은 값만 심고 return한다. **일반화 — "전환 감지" ref의 초기값은 상수가 아니라 `null`(=아직 모름)이어야 한다.** 상수로 두면 마운트가 항상 가짜 전환이 된다. **검증법**: 페이지 새로고침으론 재현이 안 된다(store가 초기화됨) — 다른 탭으로 나갔다가 그 사이 상태를 만들고 **되돌아오는** 순서로 재현하라.

56. **PM에게 "기존 유지"만 시키고 충돌 신고 통로를 안 주면 두 게임을 섞어버린다 (2026-07-19 실측)**: 테스트 회의에서 기존 개요가 "마법 카페 경영(퍼즐·힐링)"인데 지시가 "전투 시스템"이었더니, PM이 **"고객을 맞이하고 마법 음료를 만들며 고양이 기사단과 교류해 전투·회피·스킬을 활용한다"**는 합성 루프를 냈다. 팀원 산출물은 멀쩡했다(`공격력 = 레벨 × 1.5`) — **깨진 건 PM 통합 단계뿐**이다. 원인은 `pmSummaryPrompt`가 `기존 개요를 유지하되 … 처음부터 새로 쓰지 마라`만 지시하고, **"이 둘은 양립 불가"라고 말할 출구를 안 준 것**. 요청한 "산출물 간 충돌"은 산출물끼리의 충돌이지 **지시 ↔ 기존 개요 충돌이 아니다**. 그래서 PM은 섞는 것 말고 할 수 있는 게 없었다. **처방**: 갱신 전에 양립 가능성부터 판단시키고, 양립 불가면 기존 개요를 그대로 두고 `[오너 승인 필요] 컨셉 충돌: <기존> vs <지시>`로 올리게 했다. **실측(gpt-oss-120b, 실제 개요·N=4, 양방향)**:

    | | 충돌 신고 | 합성 루프 |
    |---|---|---|
    | 가드 없음(기존) | **0/4** | 4/4 |
    | **가드 적용(채택)** | **4/4** | 1/4* |
    | 가드 강화(문구 3배) | 4/4 | 1/4 |

57. **데스크톱 앱 "제대로 실행 안 됨"의 정체 = 단일 인스턴스 락을 안 걸고 whenReady가 무조건 실행된 것 (2026-07-19 결정적 재현)**: 창을 닫으면 트레이로 **숨는다**(종료 아님, main.cjs `win.on("close")`). 그 상태에서 바로가기(`🖥️ 비전엔진 데스크톱 앱.lnk` → `VisionEngine-Desktop.bat` → `npm start` → `electron .`)를 다시 누르면 두 번째 인스턴스가 뜬다. `requestSingleInstanceLock()`은 정상적으로 false를 반환하고 `app.quit()`을 부르지만, **`app.whenReady().then(connect)`가 if/else 밖에 있어 락 실패와 무관하게 실행**됐다 — 그 짧은 사이 두 인스턴스가 같은 userData의 Chromium 캐시를 다투고 `Unable to move the cache: 액세스가 거부되었습니다(0x5)` → 페이지 로드가 **ERR_FAILED(-2)** → 빈/깨진 창. 앱이 "안 켜지는" 게 아니라 **두 번째 창이 스스로를 망가뜨린 것**이다. **재현**: 인스턴스1 실행 후 인스턴스2를 띄우면 인스턴스2 로그에 `✅ 접속` + `ERR_FAILED` + 캐시 거부 3줄. **처방**: `whenReady`·`window-all-closed`·글로벌 단축키 등록을 전부 **락을 쥔 else 블록 안으로** 옮겼다 — 락 못 쥔 인스턴스는 창을 만들지 않고 즉시 물러나고, 기존 인스턴스가 `second-instance`로 창을 앞으로 가져온다. **수정 후 재현 시 인스턴스2 로그가 완전히 빈다(EXIT 0).** **교훈**: Electron에서 `requestSingleInstanceLock()` 결과로 분기했으면 `whenReady`를 포함한 **모든 부팅 로직**이 그 분기 안에 있어야 한다 — 밖에 두면 락이 있으나 마나다. 콜드 스타트(서버까지 꺼진 상태) 경로는 이 수정과 무관하게 정상: 앱이 `npm run dev`를 띄우고 접속한다.

63. **"게이트웨이 연결 끊김"이 안 풀리면 게이트웨이가 아니라 앱 서버를 봐라 (2026-07-29 오너 신고)**: 배너 `🔌 게이트웨이 이벤트 연결이 끊겼습니다 — 자동 재연결 중…`이 계속 떠 있고 복구되지 않는다는 신고. 실측하니 **게이트웨이(18789)는 ESTABLISHED로 멀쩡**했고 **Vite 앱 서버(5199)에 LISTENING이 아예 없었다** — 데스크톱 앱(PID)이 `SYN_SENT`만 반복하고 있었다. 게이트웨이 WebSocket이 Vite의 `/gateway-ws` **프록시를 지나가기 때문에**, 앱 서버가 죽으면 증상이 "게이트웨이 끊김"으로 나타난다. 원인을 정반대로 지목하는 오진이고, 이 경우 **자동 재연결은 영원히 성공하지 않는다**(붙을 서버가 없다). **진단 명령**: `netstat -ano | grep ":5199"` — LISTENING이 없으면 앱 서버 사망. **왜 죽었나**: `server.strictPort: true`라 vite.config.ts를 고칠 때마다 서버가 재시작하는데, 이전 프로세스가 포트를 놓기 전에 새 프로세스가 뜨면 **fallback 없이 그냥 죽는다**(중복 실행 방지를 위한 의도된 설정이라 그대로 둔다). **즉 vite.config.ts를 연속으로 편집하면 개발 서버가 조용히 사라질 수 있다 — 편집 세션 뒤엔 5199 생존을 확인하라.** **처방(구현)**: `App.tsx`의 `ConnBanner`가 `/api/projects`를 직접 찔러 보고, 앱 서버가 죽었으면 "게이트웨이가 아니라 웹 서버가 내려갔다 · 자동 재연결로 복구되지 않는다 · `npm run dev`를 다시 실행하라"로 **다른 배너**를 띄운다.

65. **"바로가기가 안 켜진다" = 앱은 살아 있고 복귀 경로가 예외로 죽은 것 (2026-08-06 오너 신고)**: 데스크톱 앱은 창을 닫아도 종료하지 않고 **트레이에 숨는다**(close에서 preventDefault + hide). 그래서 바로가기를 다시 누르면 두 번째 인스턴스가 뜨고, 락을 못 쥔 그쪽은 즉시 `app.quit()`하며 **기존 인스턴스의 `second-instance` 핸들러가 창을 복귀시킨다** — `showWindow()`가 앱의 **유일한 복귀 경로**다. 그런데 `win`은 창이 실제로 파괴돼도 null이 되지 않았다(`"closed"` 핸들러가 없었다). 죽은 참조가 남으면 `win.isMinimized()`가 `TypeError: Object has been destroyed`로 던지고, 그 예외가 second-instance 핸들러 안에서 나므로 **바로가기를 눌러도 화면에 아무 일도 일어나지 않는다.** 트레이 "열기"도 같은 함수라 함께 먹통. 프로세스는 4개 다 살아 있고 오류창도 로그도 없어서 사용자에겐 "실행이 안 된다"로만 보인다. **처방**: `"closed"` → `win = null` + `showWindow`에서 `isDestroyed()` 확인 + try/catch로 창 재생성 + second-instance 핸들러 래핑. **진단 순서(이 순서가 시간을 아낀다)**: ⑴ `tasklist | grep "Vision Engine"` — 프로세스가 있으면 "안 켜지는" 게 아니라 **복귀가 안 되는 것이다** ⑵ 창 핸들 확인(`MainWindowHandle`/`IsWindowVisible`) — 0이면 트레이에 숨은 상태 ⑶ 그다음에야 exe·asar·바로가기 경로를 의심하라. 이번엔 ⑶을 먼저 봤고 전부 정상이라 시간을 썼다. **재현 절차**: 바로가기 실행 → WM_CLOSE로 트레이에 숨김 → 바로가기 재클릭. **주의**: `dist-installer/*.exe`(설치본)는 win-unpacked 핫패치와 별개다 — 재설치하면 옛 버그가 되살아나므로 `npm run dist`를 다시 돌려야 하고, 그 빌드는 **win-unpacked를 지우고 다시 만들므로 앱을 끄고** 실행해야 한다.

70. **`runDevTask`의 시스템 프롬프트와 판정이 도구 현실과 어긋나 있었다 (2026-08-12)**: ⑴ 프롬프트가 도구 유무와 무관하게 *"도구로 코드를 작성·수정해라"*라고 고정돼 있었다 → 도구 개수·쓰기 가능 여부·정본 서버 유무에 따라 문장을 바꾸도록 했다(도구 0개면 *"지어내지 말고 확인 불가라고 말해라"*). ⑵ 판정이 `/❌|미흡/` → `/⚠️|조건부/` → **나머지 전부 `✅ 통과`**라서 **본문이 비어도 통과**였다. 이제 3단계 각각을 빈 응답 검사(`empty` 플래그·40자 미만·`(응답 없음)`)하고 하나라도 비면 **`⚠️ 판정 불가`** + `finish_reason`을 보여준다. **재현 검증**: `VE_DEV_MAX_TOKENS=180`으로 원 증상을 되살리니 3단계 전부 빈 응답 → 옛 코드면 `✅ 통과`, 지금은 `⚠️ 판정 불가 — 구현·리뷰·검증 단계가 빈 응답`. ⑶ **MCP 서버는 `startHub()` 시점의 "가장 최근 수정된 프로젝트"에 고정된다** — UI에서 프로젝트를 바꿔도 옛 정본을 계속 읽는다. `ensureCurrentProject()`가 작업 시작 전 kit 경로 변화를 보고 필요할 때만 재연결한다. 확인용으로 `canon__list`가 항상 루트 프로젝트 id를 먼저 출력한다.

## 3. 추천 로드맵 (다음 모델에게 — 우선순위순)

**P1 — 사용량 누적·일별 저장.** 현재 사용량(🪙)은 세션 단위라 새로고침에 날아간다. 서버에 `config/usage-log.json`(일별 append) + `/api/usage` 신설, `addUsage`에서 fire-and-forget POST, UsagePanel에 "오늘/이번 주/누적" 3줄이면 충분. 유료 API 전환 시 오너가 가장 먼저 찾을 기능.

**P1 — 노션 발행 고도화.** 지금은 텍스트 중심. 남은 것: ① 일정 섹션(## 10.) 파싱→마일스톤 표(레퍼런스의 header-column 표) ② 콜아웃 분류(작업 중/완료 — 보고서에 상태 메타 필요) ③ 아트 이미지 — 노션 external URL만 받으므로 이미지 호스팅(github raw 커밋 or imgur) 결정 필요. 컨버터는 `notion-publish.mjs`의 `mdToBlocks` 하나만 보면 된다.

**P2 — 모바일(≤900px)에서 로스터·채용 접근 불가.** 3D 좌측 패널이 숨겨진다. 하단 시트 또는 os-actions에 로스터 토글.

**P2 — 채용 직원의 GDD 섹션 헤딩 자동 삽입.** 지금은 첫 산출물 반영 시 `replaceSection`이 문서 끝에 append하며 생김. 채용 시점에 "## N. 역할 — _(아직 작성되지 않음)_"을 미리 넣어주면 GDD 목차가 즉시 완성된다 (hireApiPlugin에서 프로젝트 순회).

**P2 — 잡담·휴게실 대본 커스텀 + 관리인 임계치 UI.** `CHATTER`/`CONVOS` 배열과 `JANITOR_*` 상수를 설정으로 승격. 🪙 UsagePanel에 같이 두면 자연스럽다.

**P3 — 다이렉트 프로바이더 로컬 함수호출 검증.** 오너가 명시적으로 보류한 항목("클라우드 뗄 환경이 되면 다시 부를게"). 오너가 먼저 꺼내기 전에 착수하지 마라.

**P3 — vite.config.ts 분리.** 3,000줄에 근접. `webapp/server/`로 플러그인 단위 분리 — 기능 추가 없는 순수 리팩터링이라 오너 가치가 낮으니, 큰 기능과 겸사겸사.

**자가 성장 후속(v3.6 확장 여지)**: ① 스킬이 4개 상한(FIFO)이라 오래된 요령이 밀려난다 — 오너가 "고정(pin)"할 수 있게. ② 지금은 개인 스킬만 — 팀 공용 "베스트 프랙티스"로 승격(지식 라이브러리와 통합)하면 신입도 물려받는다. ③ 스킬이 서로 모순될 때 회고가 정리하도록. ④ 레벨을 실제 능력(예: 고레벨은 교차검토 면제, 협업 리드 우선)에 연결. 주의: XP 적립은 `store.recordGrowth` 호출 지점에만 있다 — 새 작업 종류를 추가하면 `XP_RULES`와 호출을 같이.

**아이디어 (오너가 좋아할 만한 것)**: 3D 사무실에 노션 발행 연출 — 아키비스트가 발행 시 책상에서 일어나 게시판에 문서를 붙이는 모션. 이 프로젝트의 가치는 기능이 "보이는 것"에 있다. 기능을 만들면 반드시 3D에 그 기능의 몸짓을 만들어줘라. (v3.6 레벨업 폭죽이 좋은 예 — 입사 Confetti를 재활용했다.)

## 4. 오너와 일하는 법 (관찰 기록)

- 한국어로 소통하고, **실측 증거**(스크린샷·실행 결과)를 신뢰한다. "됐습니다"만 말하지 말고 어떻게 확인했는지 보여줘라.
- 요청이 크고 방향만 준다("너가 생각한 대로 해결해줘"). **판단을 위임받으면 판단의 근거를 보고에 명시**하는 것이 신뢰를 만든다 (예: 자동 승인을 기본 꺼짐으로 한 이유).
- 비용에 민감하다 — 로컬/무료 우선, LLM 호출 없는 연출을 좋아한다. 새 기능의 호출 비용을 항상 밝혀라.
- 커밋·푸시는 라운드마다, **시크릿 스캔**(`nvapi-|ghp_|github_pat_|ntn_|secret_`) 후에. `Sample/`과 `config/*.json`(시크릿·로컬 데이터)은 커밋 금지.
- 완료 보고는 표보다 "무엇이 어떻게 되는지" 흐름으로, 남은 한계는 숨기지 말고 "알아두실 것"으로.
